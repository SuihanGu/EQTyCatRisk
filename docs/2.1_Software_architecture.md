# 2.1. Software architecture

EQTyCatRisk is organized around three functional blocks: a browser-based Web application, a data and service repository, and a Python scientific-computing engine (Fig. 1). The blocks communicate through explicit HTTP and file-based interfaces. This arrangement separates user interaction from data management and hazard–risk computation, while preserving a traceable path from input catalogues to coupled-event records and residential-loss outputs.

The scientific-computing engine is the core of the system. It reads the Japanese earthquake and typhoon catalogues together with case-specific exposure grids, standardizes JST timestamps, coordinates and hazard units, and identifies simultaneous earthquake–typhoon pairs using the project’s temporal and R30 spatial criteria. For a selected pair, it combines PGA and typhoon wind-speed fields with the Japanese residential exposure and coupled vulnerability model, then performs the Monte Carlo loss calculation. The engine returns event tables, complete typhoon tracks, grid-scale hazard/loss data and the three `without_Other` loss samples used by the application.

The data and service repository stores both source inputs and generated artefacts. It contains the earthquake and typhoon catalogues, exposure and vulnerability inputs, coupling tables, typhoon tracks, case-specific grid data, loss CSV files and loss-distribution PNG files. In the current implementation, Vite middleware provides a lightweight HTTP boundary that starts the Python workflows and exposes JSON, CSV and PNG results through stable endpoints. The browser therefore requests data and tasks through a consistent contract rather than reading Python paths or raw catalogue layouts directly.

The browser-based Web application is the user-facing layer. Built with Vue 3, TypeScript, Vite and Pinia, it provides two workflows: coupled event detection and coupled risk assessment. Leaflet presents the English-labelled map, earthquake and typhoon locations, tracks and grid heatmaps, while the result panels present event metadata and loss distributions. User selections and calculation states are returned to the same interface as maps, charts, status messages and downloadable files.

This three-block design keeps the scientific engine, data-service boundary and visual interface replaceable at different rates. New catalogues or recognition rules can be introduced in the engine; new cases can be added to the repository; and new visual summaries can be added without changing the loss model. The present implementation is scoped to Japanese earthquake–typhoon coupling and Japanese residential exposure, but the interfaces provide a basis for extension to other regions and catalogues.

## 2.1. 软件架构（中文翻译）

EQTyCatRisk 由三个功能模块组成：基于浏览器的 Web 应用、数据与服务仓库以及 Python 科学计算引擎（图 1）。三个模块通过明确的 HTTP 接口和文件接口进行通信。该结构将用户交互、数据管理和危险度—风险计算相互分离，同时保留从原始目录到耦合事件记录和住宅损失结果的可追踪处理链条。

科学计算引擎是系统的核心。它读取日本地震和台风目录以及案例对应的风险暴露网格，统一 JST 时间、坐标和危险度单位，并依据项目设定的时间条件和 R30 空间条件识别同时发生的地震—台风事件。对于选定事件，引擎将 PGA 场和台风风速场与日本住宅风险暴露数据及地震—台风耦合易损性模型进行匹配，并执行蒙特卡洛损失计算。该引擎输出耦合事件信息表、完整台风轨迹、网格尺度危险度和损失数据，以及应用程序使用的三类 `without_Other` 损失样本。

数据与服务仓库存储原始输入和生成结果，包括地震和台风目录、风险暴露与易损性输入、耦合信息表、台风轨迹、案例网格数据、损失 CSV 文件和损失分布 PNG 文件。在当前实现中，Vite 中间件提供轻量级 HTTP 边界，负责启动 Python 工作流，并通过稳定接口暴露 JSON、CSV 和 PNG 结果。因此，浏览器无需直接读取 Python 文件路径或原始目录格式，而是通过统一接口请求数据和计算任务。

基于浏览器的 Web 应用是用户交互层。系统采用 Vue 3、TypeScript、Vite 和 Pinia，提供耦合事件识别和耦合风险评估两个工作流程。Leaflet 用于展示英文底图、地震和台风位置、台风路径以及网格热力图，结果面板用于展示事件参数和损失分布。用户的选择和计算状态最终以地图、统计图、状态提示和可下载文件的形式返回到同一界面。

这种三模块结构使科学计算引擎、数据服务边界和可视化界面能够相对独立地更新。新的目录或识别规则可以在科学计算引擎中加入，新的案例可以在数据仓库中配置，新的结果摘要也可以在不改变损失模型的情况下加入前端。当前系统的适用范围为日本地震—台风耦合事件和日本住宅风险暴露，但其接口结构可为扩展到其他区域和目录提供基础。

**图 1｜EQTyCatRisk 软件架构。** 浏览器端应用向数据与服务仓库发送事件识别和风险评估请求；数据与服务仓库向 Python 科学计算引擎提供输入，计算引擎再返回耦合事件和损失结果，用于地图、统计图和文件下载。实线箭头表示请求或数据流，虚线箭头表示服务响应，彩色箭头用于区分计算流程和用户反馈路径。
